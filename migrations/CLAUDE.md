# Migrations

- **Every migration must work with the previous release.** Fly runs them in `release_command` before the canary deploy, so old code runs against the new schema during rollout, and keeps doing so after a failed or rolled-back deploy (migrations aren't rolled back). Expand in one release (nullable or defaulted columns, new tables, indexes, views alongside old ones); contract across two (ship app code that no longer references a column or table, then drop it). A rename is add + dual-write/backfill + drop across releases, never one `ALTER ... RENAME` — except in a release deployed under maintenance mode ([`docs/DEPLOYMENT.md`](../docs/DEPLOYMENT.md#maintenance-mode-deploys)), whose migration must also redefine every function body naming the column (PL/pgSQL and SQL-string bodies are text and don't follow a rename) and rename views' output columns (`ALTER VIEW … RENAME COLUMN`; view queries do follow).
- We use a custom runner (`scripts/migrate.ts`), not drizzle-kit, which isn't installed even though the file format looks like its. Run `pnpm db:migrate` / `pnpm db:migrate:test`.
- Add every migration to `meta/_journal.json`; only journaled migrations run.
- **Lock one table per migration** while writers run: index builds, drops and backfills on different tables go in separate migrations, and a backfill row-locks what it copies instead of locking tables. A transaction holding one table's lock while waiting on another's, or upgrading its own (a build, then a drop), deadlocks with a writer that holds row locks and writes the other table (a collection update does), failing the deploy (#2114). Migrations 0167 and 0169 predate this.
- Never `CREATE INDEX CONCURRENTLY` in a migration — each runs in a transaction. If production needs a concurrent build, apply it by hand first, then journal a plain `CREATE INDEX IF NOT EXISTS`. Heavy migrations on production: `docs/fly-postgres-ops.md`.
- SQL that inserts rows generates ids with `uuidv7()` (Postgres 18+).
- `CREATE OR REPLACE FUNCTION` resets every setting the new definition doesn't repeat: copy the function's `SET` lines from `schema.sql`.
- PL/pgSQL caches a static statement's plan per connection, sized for its first call: a trigger function `EXECUTE`s statements over transition tables, and one taking array arguments sets `plan_cache_mode = force_custom_plan`, or a plan for one row runs for minutes on thousands.
- Test with `pnpm test:integration`.
- Read @schema.sql and keep it current with `pnpm db:schema`.
