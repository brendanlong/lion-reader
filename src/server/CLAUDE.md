# Backend Guidelines (`src/server/`)

Diagram: `docs/diagrams/backend-api.d2`. The decisions behind the data model are in `docs/DESIGN.md`; this file holds the rules for working with it.

## Services Layer

Business logic shared by tRPC routers, the MCP server, the compat APIs and background jobs lives in `src/server/services/` as plain functions that take `db` plus parameters and return plain data, named `verbNoun` (`listEntries`, `markEntriesRead`). Routers, tools and job handlers stay thin; lint rejects a write to a core table from an API surface. Services throw the app errors in `src/server/errors.ts`; the compat APIs answer their client errors in their own format through `withClientErrors` there.

## New-Account Onboarding

Everything a new account gets goes in `runPostSignupTasks` (`src/server/auth/signup.ts`), which both signup paths call — **add steps there, not in the routes**, or the paths drift. Each task swallows its own errors; none may fail a signup.

## Site Status

The announcement banner and maintenance mode live in **Redis, not Postgres**, because maintenance mode has to work while the database is locked (`services/site-status.ts`). They are the source of truth, not a cache, so **nothing may `flushdb()`** — the deploy-time clear skips their prefix (`redis/clear-cache.ts`). The maintenance gate is in the custom server (`maintenance/server-gate.ts`); the worker and Discord bot stop touching the DB while it's on.

## Views

- **`user_feeds`**: active subscriptions merged with feed data (NULL for a subscription without a feed), including `unread_count`. **Display-only** — ownership/scoping checks query `subscriptions` directly. When grouping over a view, list every selected column in `GROUP BY`: Postgres doesn't infer functional dependencies through views (#1516).
- **`visible_entries`**: entries with visibility applied, for `entries.list/get`. It LEFT JOINs `entries` and takes `id`, `is_spam` and the sort keys from `user_entries`, so a page filtered on those reads entry rows only for the rows it returns: keep it that way (migration 0147).

## Entry Visibility

An entry is visible iff a `user_entries` row exists for `(user, entry)` and it's starred or in at least one active subscription (#1846): `user_entries.active_memberships`, which the triggers keep from `subscription_entries` and `subscriptions.unsubscribed_at`, is positive. Unsubscribing a feed and deleting a collection are the same soft delete: memberships stay and stop counting. Queries that start from `user_entries` (sync) apply it as `visibleUserEntrySql` (`services/entry-filters.ts`), which `visible-user-entry-sql.test.ts` holds to the view.

**The insert paths, not the view, keep pre-subscription content private**, so any new path that creates `user_entries` rows must only cover entries currently in the feed:

- **Subscribe time** (`populateInitialUserEntries`, for `createSubscription` and a redirect merge's survivor): the feed's current entries, `currentEntryIdsSql` (what the last poll stamped, plus what a WebSub hub announced since; a poll's disappeared check uses the same rule). A feed that is stale by its own poll cadence (`feeds.stale_at`, not the WebSub backup interval) or was never fetched instead gets a forced background refresh that fans out from a fresh fetch (`shouldRefetchOnSubscribe`).
- **Fetch time** (`entry-processor.ts`): every entry in the current fetch, idempotently, so a crash between insert and fanout self-heals on the next fetch. Archive re-announcements may fan out already read ("Backfill Guard" in `feed/CLAUDE.md`).

Starring is itself a visibility arm, so **never read a star write back through `visible_entries`** — unstarring an entry from an unsubscribed feed drops it from the view and the write looks like "not found". Read back from `user_entries` (`selectStarredEntryStates`).

## Subscription Attribution

`subscription_entries` (#1846) holds every membership in one table: an article's source subscription, its collections, and for a saved article the user's saved subscription. **Every read goes through it**: filter "entries in these subscriptions" with `buildEntriesInSubscriptionsCondition` (`services/entry-filters.ts`), one `EXISTS` (no row fan-out, so no `DISTINCT`), never a join; list pages join their list's own rows instead (Ordering & Pagination). An entry's single `subscriptionId` in the API is its **origin**, its membership in a web, email or saved subscription, an active one first; `subscriptionIds` lists every active subscription holding it. Read both with one per-row LATERAL over the entry's memberships (`entryMemberships`), never a subquery each. Membership changes move `user_entries.updated_at`, so delta sync re-delivers the entry.

**Every path that gives a user an article writes its membership itself**, in the statement that inserts the `user_entries` row (`insertUserEntriesWithMemberships`, `services/subscription-entries.ts`); collections add and remove memberships, and a redirect merge (`mergeSubscriptionIntoFeed`) copies the old subscription's into the survivor. A `user_entries` row carries no subscription: memberships alone say which subscriptions hold an article. A tag's and Uncategorized's lists have rows of their own, `tag_entries` (one per list and article; Uncategorized's list id is the user's), which triggers derive from memberships, subscriptions and tags (migration 0167). Memberships and those rows carry copies of the `user_entries` row's `read`, `starred` and `score` for their lists' indexes (migrations 0165, 0168), kept by triggers: filter and sort on them only to pick an index, read state from `user_entries`, and never write them. A membership's `position` is its own (a collection's order), not a copy.

A subscription's kind is its own `subscriptions.type` (#1846): read it there, never by joining `feeds`. Only a web subscription has a feed, and every other one keeps its name in `custom_title` (both checks; clearing an email subscription's name falls back to its sender, `clearedCustomTitle`): reach `feeds` with a LEFT JOIN, and use `NOT EXISTS` rather than `NOT IN (SELECT feed_id …)`, which a single NULL makes match nothing. A **collection** (#1806) is a subscription of type `collection`; deleting one keeps its memberships, which stop counting like an unsubscribed feed's. Its name is unique among the user's active collections ignoring case (a unique index). Renames rely on the index alone, mapping its violation to `COLLECTION_NAME_TAKEN`; create also looks the name up first, to return an existing collection (idempotent create). Test for one with `isCollectionSubscription()` (or for a web feed, `isWebSubscription()`; both in `services/subscriptions.ts`). A user's one **saved** subscription (type `saved`) is created by their first save. Its members are the Saved list (`type: "saved"`, or its id as the `subscriptionId` filter) and Google Reader's "Saved Articles" stream. Subscription lists show it (clients learn its id there, and see it in entries' `subscriptionIds`), but it's in no tag or Uncategorized and stays out of the subscription cap, counts' `subscriptions` and sync deltas, filtered with `isUserManagedSubscription()`; tagging, renaming and unsubscribing treat it as not found.

## Entry Owners

Every entry has an owner (#1846): `owner_feed_id` for a web entry (shared by every subscriber), `owner_subscription_id` for an email (its user's subscription to the sender, `subscriptions.email_sender`, unique per user) or `owner_user_id` for a saved article or upload. The owner scopes duplicate detection (a unique `(owner, guid)` per kind) and cascades deletes; **never list or count by it** — memberships do that. Exactly the owner column for the entry's type is set (`entries_owner_matches_type`), so **every lookup of an email or saved article (dedup, saved-by-URL, List-Unsubscribe) goes by its owner**, and an entry reaches `feeds` only with a LEFT JOIN.

## Unread Counts

Every badge reads one trigger-maintained counter (spam excluded; the list is in `services/counts.ts`, and `countEntries` reads any list's), never a scan (lint-enforced). Counters are defined over memberships (#1846): a subscription counts its unread memberships whether active or not (Saved is the saved subscription's count), and Tag, Uncategorized and All count **distinct** articles, since an article can reach them through several subscriptions. Migration 0133 states the rules; the database functions `apply_unread_memberships` and `recompute_list_counters` say how they're maintained. **All counter maintenance lives in the triggers** — never update a counter from app code. **Lock order is `user_entries` rows, then `subscription_entries` (a statement inserting both, `insertUserEntriesWithMemberships`, is consistent with this: its new `user_entries` rows are invisible to everyone else, so what matters is that it locks subscriptions before users, and the `user_entries` insert trigger locks users, for All, once a row has `active_memberships > 0`; so the membership insert is the main statement, whose triggers fire first. The one inversion: a redirect merge's survivor populate can add a membership to a row the user already holds through another subscription, which its trigger then updates after locking subscriptions and users. That's rare, and a deadlock there fails the fetch job, whose retry redoes the merge) (account deletion is the other exception: its cascade locks the user first, so `deleteUser` retries on deadlock), then subscriptions, then users (each sorted by id, `FOR NO KEY UPDATE`, before any statement updates several: an `UPDATE` locks rows in plan order), then tags** (the one exception: a first save creates the saved subscription before its membership, contended only by another first save for that user), in triggers and app code alike: a transaction that changes tags, subscriptions or memberships across statements takes its locks in that order first (`lockSubscriptionRow`, `lockUserEntryRows`) or it deadlocks against a concurrent mark-read. (Un)subscribing, retagging and deleting a tag move every member's `active_memberships` or tag rows (whose triggers lock the `user_entries` rows they copy state from), so they lock the members' rows first (`lockSubscriptionMembers`). An `entries` row comes before all of these: changing an entry's content writes its holders' `user_entries` rows (`entries_changed_at`), and inserting a `user_entries` row share-locks its entry (`user_entries_changed_at`), so never insert a row for an entry after locking another user's row for it. Add any new operation that moves a counter to the `OPS` of `tests/integration/list-counters-model.test.ts`. The daily `reconcile_membership_counters` job repairs drift and logs each fix at error level — **a fix means a trigger bug to investigate.**

## Row Written vs. Value Flipped

- `read_changed_at` / `starred_changed_at` are last-writer-wins watermarks: a mutation applies only if its `changedAt` (mapped to server time by `toServerTime`, capped at now) is newer. They advance on **every** accepted write, including a same-value re-assert, or a late replay could win (#1118).
- `user_entries.updated_at` moves **only on a real flip**, and so do the user-facing side effects: count aggregation, the `entry_state_changed` publish, and delta-sync redelivery (`sync.events`, Wallabag `since`). Re-asserts return no `counts`.
- Delta sync keys on `user_entries.changed_at`, the greater of the row's `updated_at` and its entry's, which triggers keep (`user_entries_changed_at`, `entries_changed_at`): **never write it from app code**, and tell a content change from a state change by the two `updated_at`s, not by it.
- The same "no churn on a non-meaningful write" rule covers entries (unchanged `content_hash` doesn't bump `updated_at`; #1084) and subscriptions (`update`/`setTags`/Google Reader rename publish and bump `updated_at` only on a real change; #1160). Capture the pre-update value in the UPDATE itself (`... AS prev` self-join), not with a pre-SELECT.

## Deletions in Delta Sync

Deltas key off change times, so a hard delete is invisible to them. **Hard-deleting an entry a client may hold must record an `entry_tombstones` row in the same transaction** (`services/entry-tombstones.ts`).

## Ordering & Pagination

- The timeline sorts by `COALESCE(published_at, fetched_at)`, denormalized onto `user_entries.published_or_fetched_at` so one index serves filter and sort. UUIDv7 `id` is only the tiebreaker.
- **A list page reads only its own rows**, through an index on (list, sort key) whose predicate holds the page's filters, except spam, which is rare enough to filter per row (#2114): All, Starred and Recently Read have partial indexes on `user_entries`, a subscription its memberships, a tag or Uncategorized its `tag_entries`. Write filters as literals (`NOT read`, not `read = $1`: a generic plan uses a partial index only for those) and keyset cursors as row comparisons (`(ts, id) < ($1, $2)`: the `OR` form is a filter, so page N reads every row above it). `list-page-bounds.test.ts` holds every list's default and unread pages, both directions, to that, so a new list or filter needs its index there.
- **Score and position sorts** (#2064) put rows without a value last in both directions, so a page reads two index ranges: the rows with a value, then those without (always newest first), with a cursor saying which range it's in (`planEntryPage`). Spell each range's `ORDER BY` exactly as its index scan returns rows, `NULLS` included, and keep the value column in the NULL range's (`IS NULL` doesn't fix it for ordering): otherwise Postgres sorts the whole range. Don't make the ranked indexes partial on the value: the NULL range would then read the timeline index past every row with a value (#2114). `list-page-bounds.test.ts` holds both ranges and the page between them.
- Build cursors with `createCursorCodec` (`services/cursor.ts`), never by hand.
- **Timestamp cursors need microseconds**: a JS `Date` truncates to milliseconds and drops or repeats rows sharing one (#680). Use `parseTimestamptz` / the `temporalTimestamp` column type (`db/temporal.ts`), and compare cursors with `Temporal.Instant.compare` (#683).

## Compat API Integer IDs

Every integer id a Google Reader or Wallabag client sees is a **stored serial** (`entries.greader_item_id`, `subscriptions`/`feeds.greader_stream_id`, `tags.greader_sortid`, `users.greader_user_id`). **Never derive one by hashing or truncating a UUID** — that had real collisions (#1117). Subscription and feed stream ids share one sequence, so a `feed/{int}` resolves to at most one of them. Google Reader shows the saved subscription as "Saved Articles" (#730); it carries the saved feed's serial, so that stream id never changed. Resolvers that reverse a client-supplied id are user-scoped (SECURITY.md §8).
