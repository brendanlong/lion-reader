# Demo Articles

- If you write a new article, ALWAYS have an Opus sub-agent explore the codebase and confirm that everything in the article is accurate
- **Write about what the reader can do, not how we built it.** Lead with the feature ("you can listen to any article"), and frame titles the same way ("Listen to Any Article"). No libraries, protocols, headers, env vars, class names, or other implementation detail users don't act on. Detail some readers will want (what data is sent where, which formats are accepted) goes in a collapsible `<details>` section placed right after the paragraph it expands on, so it's there when a reader wants it.
- **Order by importance**: within an article, the main thing it lets you do comes first, then smaller refinements ("highlighting follows the narration").
- **Broad general articles, plus narrow ones people search for**: a general article covers its whole area (Save for Later mentions files, collections, and every way to save) and links to a narrow article for each piece big enough that someone would look for it on its own (Read PDFs, Read Books). Narrow articles are for SEO: each is a page someone can land on. Fold anything smaller into the article it serves.
- **Every article has a `score`**, and lists open sorted by it. Welcome is highest by fiat. Rank the rest with an Opus subagent that sees every article: higher for what a typical visitor most wants answered ("can it save articles?", "is it free?") and what they'd find most novel or exciting, and **general over narrow**, since the general article already covers the narrow one and links to it (saving articles at all beats saving from one app). Scores are spaced by 10 so a new article can be slotted between two without renumbering; when adding one, give the judge the current order and ask where it goes.
- Name providers, apps, and sources as examples ("like NetNewsWire or Reeder"), never as complete lists, so the article doesn't go stale when support changes.
- Show, don't just tell, when the feature is visual — e.g. the plugins article embeds a real MathML equation to demo math rendering (demo contentHtml is emitted raw, so native MathML/iframes etc. just work).
- To generate a summary, use the real summary prompt from src/server/services/summarization.ts and pass it to a Sonnet subagent. Ask the agent for a 30-50 word summary (one paragraph). Put the result in `summaryHtml`, and set `summaryModelId` to the actual Sonnet model you used (currently `claude-sonnet-5`) and `summaryGeneratedAt` to today's date — these drive the "Generated by … on …" footer of the summary card, so keep them honest. Regenerating a summary? Bump both fields.
- Use the PR that implemented a feature as the article URL if possible
- Use the date the feature was implemented as the article date
- **No hero illustrations and no per-article social card** — every `/demo/...` page uses the site's default social preview. Imagery inside `contentHtml` is fine (the Discord article embeds the brand emoji from `public/emojis/`).
